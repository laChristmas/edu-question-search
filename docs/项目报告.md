# 变式题检索系统（eqsearch）项目报告

- 项目名称：`eqsearch`（edu-question-search）
- 版本：0.1.0
- 报告日期：2026-09-10
- 运行环境（实测）：Windows 10，Python 3.12 / 3.11+，AMD Ryzen 7 6800H（8 核 16 线程），32 GB 内存，NVIDIA GeForce RTX 3060 Laptop 6 GB

---

## 1. 项目概述

本系统面向教育场景的**拍照搜题**：用户只上传题目照片，系统返回**原题优先、然后变式，最多 3 条**。匹配对象是题目本身（识出的题干叙述、公式、题内附图），不是照片背景、桌面或手指。同一运算、不同故事（例如都是平均分配，但题面完全不同）**不算变式**，不会当作同类题返回。

系统不走「以图搜图」的通用视觉嵌入（不使用 CLIP / GME 等图文向量模型）。部署路径是：**OCR / 视觉语言模型把卷面读成题干与 LaTeX，再与题库对齐**；附图只用紧凑的墨迹网格和感知哈希，用来判断是否为同一张几何图，而不是用整张照片的外观去近邻搜索。

### 1.1 两条检索管线

| 开关 | 入口 | 原题定义 | 公式通道 |
|---|---|---|---|
| 公式检测开（默认） | `--math-ocr` / 页面「公式检测」 | 题干叙述 ∧ 公式模板 ∧ 附图 | 开源 VLM 整图读题，写出 LaTeX |
| 公式检测关 | `--no-math-ocr` | 题干 ∧ 附图 | 式子只当普通文字；API 里 `formula` 为 `null` |

缺图时附图项视为通过。两边都抽不出公式时公式项视为通过；**只有一侧抽到公式则不算原题**。Hendrycks MATH 不用 `solution` 做匹配；题干里的 Asymptote `[asy]...[/asy]` 作图指令会从可检索题干中剥掉。

### 1.2 返回关系

| `relation` | 含义 | 不返回的情况 |
|---|---|---|
| `original` | 同一道题（题干 / 公式 / 附图按当前管线对齐） | 无关题、仅题型相近、分数低于阈值 |
| `variant` | 结构相同且数量不同 | 短题干配不同图（如「求阴影面积」）视为无关 |
| （丢弃） | `related` / `unrelated` | 精排前丢弃，界面上看不到 |

### 2.1 在线检索流水线

```
prepare_query  →  recall(k=80)  →  mark_originals  →  tag_variants  →  rerank  →  cutoff(≤3)
     │                │                 │                  │              │           │
  题目照片          结构向量         题干∧公式∧附图      结构同、数量异    原题优先     识图题干去重
  OCR / VLM      ⊕ 附图向量          三门全过才标原题     排除短题干+不同图  线性加权     t_same=0.90
```

`search()` 按公式检测开关分流到 `search_with_formula` / `search_without_formula`。改阈值一般不必重新入库；改附图向量维数或文本编码器则必须重新 `ingest`。

## 3. 数据与题库

当前本地索引 `data/index`（`meta.json`）为试跑规模。最终部署题库按 **数十万～百万** 条规划，不能按本表线性放大稠密向量。

| 来源 | 条数 | 内容 | 题目 ID |
|---:|---:|---|---|
| APE | 5000 | 中文应用题 JSONL | 原始 `id` |
| CM17K | 17143 | 中文数学题 | `cm17k-{id}` |
| Geometry3K | 3002 | 几何题 + `img_diagram.png` | `g3k-{id}` |
| Hendrycks MATH | 12500 | 英文竞赛题（LaTeX 题干，不用解答） | `math-{split}-{subject}-{id}` |
| **合计** | **37645** | | |

入库命令将多源记录变成统一的 `GalleryItem`：展示用 `original_text`、去 LaTeX 后的 `normalized_text`、数量打成 `NUM` 的 `structure_text`，以及可选的附图 `phash` / `diagram_vector`。

Geometry3K 对外展示的 `text` 是数据集 `problem_text` 原始题干，不是 logic form；有配图的条目带 `image` 地址。MATH 的 `text` 是带 LaTeX 的 `problem`，`[asy]` 块在入库时从可检索题干中删除。

索引落盘文件（当前实测）：

| 文件 | 大小 | 作用 |
|---|---:|---|
| `vectors.npy` | **11.5 GB** | 稠密召回矩阵，形状 `(37645, 80256)` float32 |
| `items.jsonl` | 43 MB | 题干、元数据、附图向量 |
| `tfidf.joblib` | 2.8 MB | sklearn 字符 n-gram 词表 |
| `meta.json` | <1 KB | 规模与来源统计 |

维数 80256 = TF-IDF 最多 80 000 维 + 附图 16×16=256 维拼接。实现里把稀疏 TF-IDF **转成稠密数组**再 L2 归一化，因此内存占用远大于词表本身。这是部署时的第一内存瓶颈（见第 8 节）。

## 4. 各模块：模型与算法

### 4.1 配置与数据模型（`config.py` / `models.py`）

`SearchConfig` 是不可变数据类，默认阈值如下。

| 参数 | 默认 | 含义 |
|---|---:|---|
| `recall_k` | 80 | 向量召回条数 |
| `rerank_k` | 32 | 进入精排的变式上限（不含已占名额的原题） |
| `max_results` | 3 | 最终返回条数 |
| `t_same` | 0.90 | 精排去重：两条原题/变式的题干表面相似度 |
| `t_ocr_same` | 0.82 | 识图题干的原题阈值（略松，抗识别噪声） |
| `t_var` | 0.85 | 变式结构相似度 |
| `t_formula` | 0.82 | 公式模板结构相似度 |
| `t_diagram` | 0.62 | 附图墨迹余弦相似度 |
| `phash_hamming_max` | 10 | pHash 汉明距离上限（墨迹的补充） |
| `visual_blend` | 0.35 | 召回时附图向量相对题干向量的拼接权重 |
| `min_final_score` | 0.38 | 精排后截断 |
| `unrelated_structure_max` | 0.45 | 低于此结构分视为无关 |
| `generic_stem_chars` | 24 | 短于此时，不同附图不得标成变式 |

`GalleryItem` / `QueryRecord` / `ScoredCandidate` 用 Pydantic v2 建模。查询侧 `use_formula`、`from_image` 决定走哪组阈值和公式门。

### 4.2 数据集模块（`datasets/`）

**算法**：规则解析，无神经网络。

- `fetch.py`：从 GitHub / Hugging Face / Berkeley 下载 CM17K、Geometry3K、MATH。
- `loaders.py`：按文件结构自动识别来源；APE/CM17K 取 `original_text`；Geometry3K 取 `problem_text` 作展示、logic form 可进入索引文本；MATH 取 `problem`，剥 `[asy]`，答案仅从 `solution` 的 `\boxed{}` 写入元数据，**不参与匹配**。几何配图在入库时计算 pHash 与 16×16 墨迹向量。

### 4.3 文本模块（`text/`）

#### 规范化（`normalize.py`）

1. NFKC 统一全角/半角。
2. 中英文标点映射。
3. 剥 LaTeX：`\frac{a}{b}` → `(a/b)`，`\sqrt{x}` → `sqrt(x)`，去掉 `\left`/`\right`、环境与命令。
4. 去空白，得到 `normalized_text`。
5. 将整数、小数、百分数、分数替换为 `NUM`，得到 `structure_text`。保护「二次函数」「一元二次方程」等含数字的题型词，避免被当成数量。

变式分组 ID 是 `structure_text` 的 SHA-1 前 16 位。数量是否相同用有序 `(类型, 值)` 元组比较，而不是字符串相等。

#### 公式抽取与模板（`formula.py`）

从题干抽取公式跨度，做成可比对的模板。抽取来源包括：

- `$...$` / `$$...$$` 美元分隔
- `\[...\]` 展示公式
- `\begin{align*}` 等环境
- `\frac` / `\sqrt` 等命令
- 绝对值方程、字母开头的 `x = ...` 方程

跨度合并后，用与结构文本相同的数量替换得到 **公式模板 blob**。两边都空则公式门通过；一侧空一侧非空则失败。兼容判定：完全相等、结构相似度 ≥ `t_formula`、词袋相同、或较短模板是较长模板的子串（缓解 OCR 漏分式）。

另外会把公式从题干中遮成占位符 `EQ`，原题的「题干门」只比叙述，避免和公式通道重复计分。MATH 的 Asymptote 源码在抽取前删除。OCR 修复：Unicode 减号归一、方括号绝对值改回竖线。

**该模块没有模型**，全是正则与字符串模板。

#### 相似度（`similarity.py`）

无学习排序模型。两条分数都是：

- 表面相似：`0.6 * SequenceMatcher.ratio + 0.4 * 字符 3-gram Jaccard`
- 结构相似：`0.5 * SequenceMatcher.ratio + 0.5 * 字符 3-gram Jaccard`

`SequenceMatcher` 来自 Python 标准库 `difflib`（最长匹配块比）。Jaccard 在字符 3-gram 集合上计算。

### 4.4 视觉模块（`vision/`）

这是部署时**唯一必须加载深度模型**的部分。路径是「读字 + 裁附图」，不是端到端图像检索。

```
题目照片
  ├─ RapidOCR（ONNX，PP-OCR）──► 文字框、阅读顺序题干（公式关时直接当查询）
  ├─ 公式开：PaddleOCR-VL 或 Qwen2.5-VL ──► 整图抄题 + LaTeX
  └─ 文字框外的大块墨迹 ──► 附图裁剪 ──► 16×16 墨迹向量 + pHash
```

#### 文字检测 / 识别：RapidOCR

- **库**：`rapidocr` ≥ 2.0 + `onnxruntime`
- **模型族**：PP-OCRv4 检测 + 识别（ONNX），默认走 CPU
- **用途**：得到文本行框；公式检测开启时这些框只用来**裁附图、排阅读顺序**，题干正文被 VLM 覆盖
- **可选**：`ocr=paddle` 时用传统 PaddleOCR（需另装），同样只当文字框引擎

`layout.py` 按行高中位数分行阅读；丢掉过短的点名标注（如单独的 `O`、`CBD`）。附图裁剪：灰度墨迹（像素值小于 180）减去文字框膨胀区域，OpenCV 连通域（无 cv2 时退化为外接矩形），丢掉几乎铺满整页的背景，最多保留 2 块最大图。**禁止把整张手机照片当作附图做哈希。**

#### 整图读题（公式检测开）

优先级由环境变量 `EQSEARCH_VISION_READER` 控制：`auto`（默认先 PaddleOCR-VL，失败再 Qwen）/ `paddleocr-vl` / `qwen` / `off`。

| 后端 | 模型 | 框架 | 本机状态 |
|---|---|---|---|
| **PaddleOCR-VL**（优先） | PaddleOCR-VL 1.x 文档解析 VL（约 0.9B 级） | PaddlePaddle 3.2 GPU + `paddleocr[doc-parser]` 3.7 | **已安装并作为当前读图引擎** |
| **Qwen2.5-VL-3B**（回退） | `Qwen/Qwen2.5-VL-3B-Instruct`（可用 `EQSEARCH_QWEN_VL` 覆盖） | PyTorch + Transformers，CUDA 上 FP16 | 本机未装 torch，未启用 |
| 关闭 | — | 退回 RapidOCR 纯文字 | 公式门变弱 |

提示词要求：只抄题目正文，公式写在 `$...$` 中，不解题、不描述背景。输出会去掉 markdown 围栏、把 `\(...\)` 转成美元公式，并在「解答/答案」行截断。服务启动时 `warmup_vision_reader()` 预热，避免第一次检索卡在加载权重。推理加进程内锁，**同一进程同时只跑一张图**。

长边默认缩到 `EQSEARCH_VL_MAX_SIDE=1024`，避免手机原图把 6 GB 显存打满。含 `pmatrix`/`bmatrix` 等矩阵环境时丢弃附图裁剪，以免把排版矩阵当成几何图、把无图 MATH 金标挤出召回。

#### 附图表示（无深度视觉模型）

| 特征 | 算法 | 维数 / 形式 | 相似度 |
|---|---|---|---|
| 墨迹网格 | 紧裁墨迹 → 垫成正方形 128×128 → 二值化（可选膨胀）→ 缩到 16×16 | 256 维 float，L2 归一 | 余弦 ≥ `t_diagram` |
| 感知哈希 | `imagehash.phash`（DCT 64-bit） | 十六进制串 | 汉明距离 ≤ 10 |

多块附图对墨迹向量取均值再归一。颜色直方图接口仍保留，但已改成墨迹向量的别名，避免用背景颜色匹配。

### 4.5 编码器与向量索引（`encode/` / `index/`）

#### 题干编码器（当前默认）

**算法**：字符级 TF-IDF，**稠密**召回。

- `TfidfVectorizer(analyzer="char", ngram_range=(2, 4), max_features=80000, norm="l2")`
- 对 `structure_text`（数量已打成 `NUM`）拟合；`encode()` 把稀疏矩阵 **`.toarray()`** 成稠密阵再 L2 归一化
- 与 256 维附图按 `visual_blend=0.35` 拼接，得到 80 256 维，全库内积取 `recall_k=80`

字符重叠对公式残片、中英混排和「不同故事不算变式」友好。这是当前试跑与评测路径；百万级体积见第 8 节，正式部署可改稀疏倒排或句向量，**尚未改默认代码**。

#### 可选句向量（正式部署候选）

`SentenceTransformerEncoder`，默认 `BAAI/bge-small-zh-v1.5`（约 33M 参数、384 维）。入库时 `--encoder sbert`。本仓库当前索引**未使用** SBERT。正式部署若改用句向量，内存下降两个数量级，但需重新 ingest，中英混合题库要评估英文 MATH，且语义近邻可能召回「同类题」。

#### 近邻检索（当前）

默认 **`VectorIndex`**（`vectors.npy`）：NumPy 全库内积，装了 `faiss-cpu` 时用 `IndexFlatIP`。正式部署换法见 8.4。

### 4.6 原题、变式与精排（`pipeline/`）

**没有交叉编码器、没有学习 to-rank。** 全部是规则 + 上述相似度。

#### 原题（`filter_original.py`）

必须同时通过：

1. **题干门**：公式开时先遮公式再比叙述。数量一致且表面相似 ≥ `t_ocr_same`；或规范化后包含关系（OCR 把图注拼进题干时的容忍）。
2. **公式门**（仅公式开）：模板兼容，或拆成原子公式集合相等。
3. **附图门**：任一侧无图则通过；否则墨迹余弦或 pHash 过阈值。

#### 变式（`variant.py`）

非原题且数量不同、结构分 ≥ `t_var` → `variant`。结构分过低 → `unrelated`。短题干且附图明显不同 → 强制 `unrelated`（避免「求 x」配不同几何图被当成变式）。

#### 精排（`rerank.py`）

只保留原题或变式。原题最终分：

\[
1.2 + 0.1 \times \text{retrieval\_score}
\]

变式为结构、召回分、公式分、附图分、结构-表面差的线性组合，并减去表面分（抑制「字面很像但结构不够」）。排序关键字：`(不是原题, -final_score)`，因此原题永远在变式前面。

`cutoff`：低于 `min_final_score` 丢弃；与已保留条目同类型且表面相似 ≥ `t_same` 视为重复丢掉（**只比文本，不比图**）；满 3 条停止。

### 4.7 HTTP 与 CLI（`api/` / `cli.py`）

- FastAPI + Uvicorn。部署接口 `POST /v1/search` 为 `multipart/form-data`，用户只上传 `image`（另可传 `math_ocr`）。
- 识图与检索放在线程池，避免阻塞事件循环；VLM 内部仍串行。
- `GET /health` 返回索引规模；`GET /v1/items/{id}/image` 返回入库时的本地配图。
- 静态页 `api/static/index.html` 只提供图片上传与公式检测开关（记在 `localStorage`）。

### 4.8 评测（`pipeline/eval_metrics.py` + `data/eval/`）

部署评测走**渲染图**：`formula_10k` 按来源配额抽 10000 题，白底渲染（MATH / Geometry3K 用 Tectonic 编 LaTeX），再走与线上一致的识图管线。指标：命中@3、首位、是否标成原题、误标其他原题、空结果、时延。

## 5. 评测结果摘要（formula_10k 渲染图，2026-09-10）

索引 37645 条；查询 10000 张渲染题图（APE 1328 / CM17K 4554 / Geometry3K 797 / MATH 3321）。Geometry3K 关公式检测（题干 ∧ 附图）；其余开公式检测。这是与部署一致的拍照管线，不是把库内题干当查询。

| 分组 | 样本 | 命中@3 | 空结果 | 均耗时 |
|---|---:|---:|---:|---:|
| 总体 | 10000 | **86.8%** | 8.2% | **3.90 s** |
| APE | 1328 | 99.5% | 0.4% | 3.48 s |
| CM17K | 4554 | 92.1% | 0.0% | 4.63 s |
| Geometry3K | 797 | 41.0% | 50.9% | 0.85 s |
| MATH | 3321 | 85.2% | 12.3% | 3.79 s |

时延几乎全部在 VLM 读题（约 4 s/张）。Geometry3K 关公式后走 RapidOCR，时延降到 0.85 s，但 RapidOCR 会把图上数字读进题干，原题三门更严，空结果约一半。MATH 剩余约 15% 未命中，主要是公式模板对不齐、以及 `[asy]` 图未画进评测 PNG 导致召不回。各来源失败用例见 [测试报告](测试报告.md)。

## 6. 模块—模型对照表

| 模块 | 是否深度学习 | 具体模型 / 算法 | 训练与否 |
|---|---|---|---|
| 数据加载 | 否 | 规则解析 | — |
| 文本规范化 / 公式模板 | 否 | 正则、数量替换 | — |
| 题干/结构相似 | 否 | difflib + 3-gram Jaccard | — |
| 召回编码 | 否（默认） | 字符 2–4 gram TF-IDF，稠密 80 000 维 | 仅在题库上拟合 IDF |
| 召回编码（可选） | 是 | bge-small-zh-v1.5（正式部署候选） | 用官方预训练，不微调 |
| 近邻 | 否 | 稠密内积 / 可选 Faiss Flat | — |
| 文字框 | 是 | RapidOCR / PP-OCRv4 ONNX | 预训练 |
| 整图读题 | 是 | **PaddleOCR-VL** 或 Qwen2.5-VL-3B | 预训练，不微调 |
| 附图 | 否 | 16×16 墨迹网格 + pHash | — |
| 原题/变式/精排 | 否 | 阈值规则 + 线性加权 | — |
| 服务 | 否 | FastAPI / Uvicorn | — |

结论：系统是**拍照检索管道**，不是端到端答题或生成模型。GPU 用于公式检测时的视觉读题，与题库条数无关。与题库对齐当前是稠密 TF-IDF + 规则。正式部署到百万级时可改稀疏倒排或句向量，见第 8.4 节。

## 7. 部署形态

最终目标是用户**只上传题目照片**。可运行的形态：

1. **产品默认（公式检测开）**：RapidOCR 裁图 + PaddleOCR-VL 读题 + 题干 ∧ 公式 ∧ 附图。需要 NVIDIA GPU 与 `paddlepaddle-gpu`。
2. **公式检测关**：RapidOCR 识题干 + 裁图，原题 = 题干 ∧ 附图。CPU 可跑，适合几何配图为主、公式门会误杀的场景。

进程模型：单 Uvicorn worker 即可；VLM 有全局锁，多 worker 会在 GPU 上争用显存。数万条试跑时题库可整库载入内存。百万级应把向量和条目外置（Faiss / SQLite），检索页不提供题干输入框。详第 8 节。

---

## 8. 部署硬件评估

评估分两层：本机 **3.8 万条**已跑通的拍照管线，以及最终题库 **数十万～百万级** 的外推。读图模型的显存几乎不随题库变大；真正随 N 线性膨胀的是**召回向量**和**条目元数据**。当前默认实现（稠密 80 256 维 TF-IDF ⊕ 附图 + 全库内积）在百万级不可用，必须换模块算法，详见 8.4。

规模记号：N = 题库条数；当前实测 N = 37 645。内存按 float32、未压缩估算。

### 8.1 本机实测（3.8 万条，现实现）

| 项目 | 配置 |
|---|---|
| 整机 | ASUS TUF Gaming A15 FA507RM |
| CPU | AMD Ryzen 7 6800H，8 核 16 线程，3.2 GHz |
| 内存 | **32 GB**（约 31.2 GB 可用） |
| GPU | **RTX 3060 Laptop 6 GB**，驱动 572.47 |
| 读图 | PaddlePaddle 3.2.2 GPU + PaddleOCR 3.7（PaddleOCR-VL），权重缓存约 1.9 GB（`~/.paddlex`） |
| 索引 | 11.5 GB `vectors.npy`（形状 `(37645, 80256)`）+ 43 MB 条目 |
| 图搜时延 | 约 **3.5–4.6 s/查询**（公式开，几乎全在 VLM） |
| 并发 | 单请求串行（VLM 锁） |

6 GB 显存能跑通的前提是 `EQSEARCH_VL_MAX_SIDE=1024`。更大原图会在视觉编码器里涨显存直至卡住。

### 8.2 资源拆解：随 N 缩放 vs 不随 N 缩放

**不随题库变大（每台推理机一份）：**

| 组件 | 内存 | 显存 | 磁盘 | 说明 |
|---|---|---|---|---|
| RapidOCR ONNX | 0.3–0.8 GB | 0（默认 CPU） | 数十 MB | 每张查询图都跑 |
| PaddleOCR-VL | 1–2 GB | **约 4–6 GB** | ~2 GB | 公式开；与 N 无关 |
| Qwen2.5-VL-3B FP16 | 数 GB | **约 6–8 GB+** | ~7 GB | 回退；不要与 PaddleOCR-VL 同时常驻 |
| FastAPI / Python / OS | 3–5 GB | 0 | — | Windows 余量不可忽略 |

读图时延（约 4 s）和 GPU 占用由**并发查询数**决定，不由题库规模决定。百万题库仍是「一卡一路 VLM」除非加卡或排队。

**随 N 线性变大（当前实现）：**

稠密召回矩阵体积为 \(N \times 80256 \times 4\) 字节（80 000 维 TF-IDF + 256 维附图）。条目按本机 43 MB / 37 645 ≈ 1.1 KB/条 计 jsonl；进程内 Pydantic 对象大约再乘 2–4 倍。

| N | 稠密 `vectors.npy` | jsonl 条目 | 进程内条目（估） | 全库内积一次（约） |
|---:|---:|---:|---:|---|
| 3.8 万（现状） | **11.5 GB**（实测） | 43 MB | 0.5–1 GB | 可接受，读图更慢 |
| 20 万 | **64 GB** | 0.23 GB | 1–2 GB | 内存带宽瓶颈，秒级 |
| 50 万 | **161 GB** | 0.57 GB | 2–5 GB | 单机装不下 |
| 100 万 | **321 GB** | 1.1 GB | 4–8 GB | 不可部署 |

若再启用 `faiss-cpu` 的 `IndexFlatIP` 且仍保留 NumPy 副本，向量内存接近**再翻一倍**（百万级约 640 GB）。结论：现实现的内存墙在 **10 万条之前**就会撞上 64–128 GB 服务器；百万级必须换算法，而不是买更大内存条硬扛 80k 维稠密阵。

### 8.3 现实现下的档位（仅适用于数万条试跑）

拍照检索，公式检测开，N ≈ 4 万：

| 项 | 最低可跑（已验证） | 建议试跑 |
|---|---|---|
| GPU | NVIDIA **6 GB**（3060 Laptop） | **8 GB**（少翻车） |
| 内存 | **32 GB** | 32 GB |
| CPU | 8 核 | 同左 |
| 磁盘 SSD | 30 GB | 50 GB+ |
| 长边 | `EQSEARCH_VL_MAX_SIDE=1024` | 同左 |
| 并发 | **1 路图搜 / GPU** | 排队，不要多 worker 抢 6 GB 卡 |
| 时延 | 3.5–5 s | 吞吐受 VLM 限制 |

**不要**用现实现去估百万级采购：按上表线性放大内存会得到「一台机器 300 GB 内存」的错误结论。

### 8.4 正式部署时可换的索引（当前仍是稠密）

当前代码与 `formula_10k` 评测走 **稠密字符 TF-IDF ⊕ 附图拼接 + 全库内积**（`TfidfBiEncoder.encode()` 做 `.toarray()`，`VectorIndex` 写 `vectors.npy`）。原题/变式门建立在这套字符 n-gram 余弦上，数万条试跑可用。百万级不能按这条路径线性放大（100 万条约 **321 GB**）。

正式部署到数十万～百万条时，可在入库前改编码器或近邻，**默认实现尚未切换**。两条候选：

| | 方案 A：稀疏 TF-IDF + 倒排 | 方案 B：句向量（SBERT）+ 低维 ANN |
|---|---|---|
| 怎么做 | `encode()` 保持 CSR，CSC 列作 posting，查询只累加出现过的 n-gram | 入库 `--encoder sbert`；Faiss HNSW / IVF（384～768 维） |
| 与现网关系 | 同一套字符 2–4 gram，原题/变式阈值可沿用 | 须重新 ingest 与渲染图评测 |
| 百万级体积 | 约 **1–2 GB** 稀疏矩阵（每题约 100–200 个非零 n-gram） | 100 万×384×4 B ≈ **1.5 GB**；INT8 可再压 |
| 优点 | 「不同故事、同一运算」不会被语义近邻挤进召回 | 接标准 ANN，内存与查询都按低维设计 |
| 注意 | 不要把 8 万维再灌进 Faiss / Milvus；附图不要拼进召回维 | 中英库不要只用 `bge-small-zh`；语义近邻可能召回同类题，精排结构门仍要挡住 |

不要把当前 80 256 维稠密阵送进向量库。无论 A 还是 B，条目不要百万级 Pydantic 全驻留（改为 SQLite / 按 id 读取）；读图仍用 PaddleOCR-VL，GPU 只服务查询图片。

### 8.5 换索引后的硬件档位

两套方案的索引都可以落在 **32 GB** 单机上；GPU 仍按读图配置，不随题库条数加显存。

| 项 | 50 万题，单机 | 100 万题，单机 | 100 万题，读图与索引分离 |
|---|---|---|---|
| 索引内存 | 约 1–8 GB | 约 2–16 GB（含条目缓存） | 索引机 8–16 GB（含 SQLite） |
| 读图 GPU | 1× 8 GB（T4 / 3060 / 4060） | 1× 8 GB 起 | 按 QPS 加卡 |
| 机器内存 | **32 GB** | **32 GB** | 索引 32 GB；读图机 16 GB |
| CPU | 8 核 | 8–16 核 | 索引 8 核；读图 4 核+ |
| 磁盘 SSD | 100 GB+ | 200 GB+（不含百万原图） | 图存对象存储 |
| 查询时延 | 约 3–5 s（读图）+ 检索毫秒～几十毫秒 | 同左 | 读图并行后 QPS 随卡数上升 |
| 并发 | 1 路 VLM / 卡 | 同左 | 队列 + 多卡 |

对比：若正式部署仍用当前稠密 80 256 维，100 万题仅矩阵约 321 GB，单机不可用。

### 8.6 正式部署时降低硬件的顺序

1. **换召回**：稀疏 TF-IDF 倒排，或 SBERT + HNSW/IVF。不改这一项，后面买内存、装高维 Faiss 都没有意义。
2. **召回与附图拆开**，去掉 80 256 维拼接（方案 A 必做；方案 B 附图只在 top-k 比）。
3. **条目按 id 加载**，避免百万 Pydantic 常驻。
4. **读图保持 PaddleOCR-VL**；量化/TensorRT 只为提高 QPS。上传图强制长边 1024。
5. 更高 QPS：加读图 GPU + 队列，而不是加索引内存。

不推荐：把当前 8 万维 TF-IDF 灌进 Milvus/HNSW；用句向量替换精排里的结构门；CPU 跑 VLM 当交互服务；多 worker 抢一块 6 GB 卡。

## 9. 结论

eqsearch 的部署形态是**拍照搜题**：用户只上传题目照片。RapidOCR 框字并裁附图，PaddleOCR-VL 把卷面抄成带 LaTeX 的题干，再与题库对齐：题干 / 公式模板 / 附图三门判定原题，结构相似且数量不同判定变式，最多返回 3 条。不依赖 CLIP 类图像向量。

当前实现是 **稠密字符 TF-IDF ⊕ 附图 + 全库内积**。在 **37 645** 条上渲染图命中@3 为 **86.8%**，约 4 秒/张，本机 32 GB 内存 + 6 GB 显卡可跑。正式部署到 **数十万～百万** 条时，不要线性放大这条稠密路径（百万约 **321 GB**）；可改 **稀疏 TF-IDF + 倒排**，或 **SBERT + 低维 ANN**。换索引后，百万级可落在 **32 GB 内存** 的单机上，GPU 仍按读图并发配置 **6–8 GB 起、一路一卡**。
