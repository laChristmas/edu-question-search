# 变式题检索系统（eqsearch）项目报告

- 项目名称：`eqsearch`（edu-question-search）
- 版本：0.1.0
- 报告日期：2026-09-10
- 运行环境（实测）：Windows 10，Python 3.12 / 3.11+，AMD Ryzen 7 6800H（8 核 16 线程），32 GB 内存，NVIDIA GeForce RTX 3060 Laptop 6 GB

---

## 1. 项目概述

本系统面向教育场景的**题目检索**：用户粘贴题干或上传题目照片，系统返回**原题优先、然后变式，最多 3 条**。匹配对象是题目本身（题干叙述、公式、题内附图），不是照片背景、桌面或手指。同一运算、不同故事（例如都是平均分配，但题面完全不同）**不算变式**，不会当作同类题返回。

系统刻意不走「以图搜图」的通用视觉嵌入（不使用 CLIP / GME 等图文向量模型）。图像路径是：**OCR / 视觉语言模型把卷面转成文字与 LaTeX，再做文本检索**；附图只用紧凑的墨迹网格和感知哈希，用来判断是否为同一张几何图，而不是用整张照片的外观去近邻搜索。

### 1.1 两条检索管线

| 开关 | 入口 | 原题定义 | 公式通道 |
|---|---|---|---|
| 公式检测开（默认） | `--math-ocr` / 页面「公式检测」 | 题干叙述 ∧ 公式模板 ∧ 附图 | 开源 VLM 整图读题，写出 LaTeX |
| 公式检测关 | `--no-math-ocr` | 题干 ∧ 附图 | 式子只当普通文字；API 里 `formula` 为 `null` |

缺图时附图项视为通过。两边都抽不出公式时公式项视为通过；**只有一侧抽到公式则不算原题**。Hendrycks MATH 不用 `solution` 做匹配；题干里的 Asymptote `[asy]...[/asy]` 作图指令会从可检索题干中剥掉。

### 1.2 返回关系

| `relation` | 含义 | 不返回的情况 |
|---|---|---|
| `original` | 同一道题（题干 / 公式 / 附图按当前管线对齐） | 无关题、仅题型相近、分数低于阈值 |
| `variant` | 结构相同且数量不同 | 短题干配不同图（如「求阴影面积」）视为无关 |
| （丢弃） | `related` / `unrelated` | 精排前丢弃，界面上看不到 |

## 2. 仓库与模块结构

Python 包位于 `src/eqsearch/`，可编辑安装：`pip install -e ".[dev]"`。可选附加：`[faiss]` 加速向量检索、`[sbert]` 换句向量、`[paddle-vl]` 装 PaddleOCR-VL、`[vlm]` 装 Qwen2.5-VL。

### 2.1 在线检索流水线

```
prepare_query  →  recall(k=80)  →  mark_originals  →  tag_variants  →  rerank  →  cutoff(≤3)
     │                │                 │                  │              │           │
  文本或拍照        结构向量         题干∧公式∧附图      结构同、数量异    原题优先     文本去重
  OCR / VLM      ⊕ 附图向量          三门全过才标原题     排除短题干+不同图  线性加权     t_same=0.90
```

`search()` 按公式检测开关分流到 `search_with_formula` / `search_without_formula`。改阈值一般不必重新入库；改附图向量维数或文本编码器则必须重新 `ingest`。

## 3. 数据与题库

当前本地索引 `data/index`（`meta.json`）：

| 来源 | 条数 | 内容 | 题目 ID |
|---:|---:|---|---|
| APE | 5000 | 中文应用题 JSONL | 原始 `id` |
| CM17K | 17143 | 中文数学题 | `cm17k-{id}` |
| Geometry3K | 3002 | 几何题 + `img_diagram.png` | `g3k-{id}` |
| Hendrycks MATH | 12500 | 英文竞赛题（LaTeX 题干，不用解答） | `math-{split}-{subject}-{id}` |
| **合计** | **37645** | | |

入库命令将多源记录变成统一的 `GalleryItem`：展示用 `original_text`、去 LaTeX 后的 `normalized_text`、数量打成 `NUM` 的 `structure_text`，以及可选的附图 `phash` / `diagram_vector`。

Geometry3K 对外展示的 `text` 是数据集 `problem_text` 原始题干，不是 logic form；有配图的条目带 `image` 地址。MATH 的 `text` 是带 LaTeX 的 `problem`，`[asy]` 块在入库时从可检索题干中删除。

索引落盘文件（当前实测）：

| 文件 | 大小 | 作用 |
|---|---:|---|
| `vectors.npy` | **11.5 GB** | 稠密召回矩阵，形状 `(37645, 80256)` float32 |
| `items.jsonl` | 43 MB | 题干、元数据、附图向量 |
| `tfidf.joblib` | 2.8 MB | sklearn 字符 n-gram 词表 |
| `meta.json` | <1 KB | 规模与来源统计 |

维数 80256 = TF-IDF 最多 80 000 维 + 附图 16×16=256 维拼接。实现里把稀疏 TF-IDF **转成稠密数组**再 L2 归一化，因此内存占用远大于词表本身。这是部署时的第一内存瓶颈（见第 8 节）。

## 4. 各模块：模型与算法

### 4.1 配置与数据模型（`config.py` / `models.py`）

`SearchConfig` 是不可变数据类，默认阈值如下。

| 参数 | 默认 | 含义 |
|---|---:|---|
| `recall_k` | 80 | 向量召回条数 |
| `rerank_k` | 32 | 进入精排的变式上限（不含已占名额的原题） |
| `max_results` | 3 | 最终返回条数 |
| `t_same` | 0.90 | 文本查询的原题题干表面相似度 |
| `t_ocr_same` | 0.82 | 拍照 OCR 题干阈值（略松，抗识别噪声） |
| `t_var` | 0.85 | 变式结构相似度 |
| `t_formula` | 0.82 | 公式模板结构相似度 |
| `t_diagram` | 0.62 | 附图墨迹余弦相似度 |
| `phash_hamming_max` | 10 | pHash 汉明距离上限（墨迹的补充） |
| `visual_blend` | 0.35 | 召回时附图向量相对文本向量的拼接权重 |
| `min_final_score` | 0.38 | 精排后截断 |
| `unrelated_structure_max` | 0.45 | 低于此结构分视为无关 |
| `generic_stem_chars` | 24 | 短于此时，不同附图不得标成变式 |

`GalleryItem` / `QueryRecord` / `ScoredCandidate` 用 Pydantic v2 建模。查询侧 `use_formula`、`from_image` 决定走哪组阈值和公式门。

### 4.2 数据集模块（`datasets/`）

**算法**：规则解析，无神经网络。

- `fetch.py`：从 GitHub / Hugging Face / Berkeley 下载 CM17K、Geometry3K、MATH。
- `loaders.py`：按文件结构自动识别来源；APE/CM17K 取 `original_text`；Geometry3K 取 `problem_text` 作展示、logic form 可进入索引文本；MATH 取 `problem`，剥 `[asy]`，答案仅从 `solution` 的 `\boxed{}` 写入元数据，**不参与匹配**。几何配图在入库时计算 pHash 与 16×16 墨迹向量。

### 4.3 文本模块（`text/`）

#### 规范化（`normalize.py`）

1. NFKC 统一全角/半角。
2. 中英文标点映射。
3. 剥 LaTeX：`\frac{a}{b}` → `(a/b)`，`\sqrt{x}` → `sqrt(x)`，去掉 `\left`/`\right`、环境与命令。
4. 去空白，得到 `normalized_text`。
5. 将整数、小数、百分数、分数替换为 `NUM`，得到 `structure_text`。保护「二次函数」「一元二次方程」等含数字的题型词，避免被当成数量。

变式分组 ID 是 `structure_text` 的 SHA-1 前 16 位。数量是否相同用有序 `(类型, 值)` 元组比较，而不是字符串相等。

#### 公式抽取与模板（`formula.py`）

从题干抽取公式跨度，做成可比对的模板。抽取来源包括：

- `$...$` / `$$...$$` 美元分隔
- `\[...\]` 展示公式
- `\begin{align*}` 等环境
- `\frac` / `\sqrt` 等命令
- 绝对值方程、字母开头的 `x = ...` 方程

跨度合并后，用与结构文本相同的数量替换得到 **公式模板 blob**。两边都空则公式门通过；一侧空一侧非空则失败。兼容判定：完全相等、结构相似度 ≥ `t_formula`、词袋相同、或较短模板是较长模板的子串（缓解 OCR 漏分式）。

另外会把公式从题干中遮成占位符 `EQ`，原题的「题干门」只比叙述，避免和公式通道重复计分。MATH 的 Asymptote 源码在抽取前删除。OCR 修复：Unicode 减号归一、方括号绝对值改回竖线。

**该模块没有模型**，全是正则与字符串模板。

#### 相似度（`similarity.py`）

无学习排序模型。两条分数都是：

- 表面相似：`0.6 * SequenceMatcher.ratio + 0.4 * 字符 3-gram Jaccard`
- 结构相似：`0.5 * SequenceMatcher.ratio + 0.5 * 字符 3-gram Jaccard`

`SequenceMatcher` 来自 Python 标准库 `difflib`（最长匹配块比）。Jaccard 在字符 3-gram 集合上计算。

### 4.4 视觉模块（`vision/`）

这是部署时**唯一必须加载深度模型**的部分。路径是「读字 + 裁附图」，不是端到端图像检索。

```
题目照片
  ├─ RapidOCR（ONNX，PP-OCR）──► 文字框、阅读顺序题干（公式关时直接当查询）
  ├─ 公式开：PaddleOCR-VL 或 Qwen2.5-VL ──► 整图抄题 + LaTeX
  └─ 文字框外的大块墨迹 ──► 附图裁剪 ──► 16×16 墨迹向量 + pHash
```

#### 文字检测 / 识别：RapidOCR

- **库**：`rapidocr` ≥ 2.0 + `onnxruntime`
- **模型族**：PP-OCRv4 检测 + 识别（ONNX），默认走 CPU
- **用途**：得到文本行框；公式检测开启时这些框只用来**裁附图、排阅读顺序**，题干正文被 VLM 覆盖
- **可选**：`ocr=paddle` 时用传统 PaddleOCR（需另装），同样只当文字框引擎

`layout.py` 按行高中位数分行阅读；丢掉过短的点名标注（如单独的 `O`、`CBD`）。附图裁剪：灰度墨迹（像素值小于 180）减去文字框膨胀区域，OpenCV 连通域（无 cv2 时退化为外接矩形），丢掉几乎铺满整页的背景，最多保留 2 块最大图。**禁止把整张手机照片当作附图做哈希。**

#### 整图读题（公式检测开）

优先级由环境变量 `EQSEARCH_VISION_READER` 控制：`auto`（默认先 PaddleOCR-VL，失败再 Qwen）/ `paddleocr-vl` / `qwen` / `off`。

| 后端 | 模型 | 框架 | 本机状态 |
|---|---|---|---|
| **PaddleOCR-VL**（优先） | PaddleOCR-VL 1.x 文档解析 VL（约 0.9B 级） | PaddlePaddle 3.2 GPU + `paddleocr[doc-parser]` 3.7 | **已安装并作为当前读图引擎** |
| **Qwen2.5-VL-3B**（回退） | `Qwen/Qwen2.5-VL-3B-Instruct`（可用 `EQSEARCH_QWEN_VL` 覆盖） | PyTorch + Transformers，CUDA 上 FP16 | 本机未装 torch，未启用 |
| 关闭 | — | 退回 RapidOCR 纯文字 | 公式门变弱 |

提示词要求：只抄题目正文，公式写在 `$...$` 中，不解题、不描述背景。输出会去掉 markdown 围栏、把 `\(...\)` 转成美元公式，并在「解答/答案」行截断。服务启动时 `warmup_vision_reader()` 预热，避免第一次检索卡在加载权重。推理加进程内锁，**同一进程同时只跑一张图**。

长边默认缩到 `EQSEARCH_VL_MAX_SIDE=1024`，避免手机原图把 6 GB 显存打满。含 `pmatrix`/`bmatrix` 等矩阵环境时丢弃附图裁剪，以免把排版矩阵当成几何图、把无图 MATH 金标挤出召回。

#### 附图表示（无深度视觉模型）

| 特征 | 算法 | 维数 / 形式 | 相似度 |
|---|---|---|---|
| 墨迹网格 | 紧裁墨迹 → 垫成正方形 128×128 → 二值化（可选膨胀）→ 缩到 16×16 | 256 维 float，L2 归一 | 余弦 ≥ `t_diagram` |
| 感知哈希 | `imagehash.phash`（DCT 64-bit） | 十六进制串 | 汉明距离 ≤ 10 |

多块附图对墨迹向量取均值再归一。颜色直方图接口仍保留，但已改成墨迹向量的别名，避免用背景颜色匹配。

### 4.5 编码器与向量索引（`encode/` / `index/`）

#### 文本编码器（默认）

**算法**：字符级 TF-IDF 双塔（查询与题库共用同一套权值）。

- `TfidfVectorizer(analyzer="char", ngram_range=(2, 4), max_features=80000)`
- 对 `structure_text`（数量已打成 `NUM`）拟合
- `transform` 后转为 float32 稠密阵并按行 L2 归一化
- 入库时与附图向量拼接：`concat(text, 0.35 * diagram)`，再整体 L2 归一化；无图行附图为零，不贡献方向

这不是神经网络。中英文、LaTeX 残留、数字结构都能靠字符 n-gram 重叠召回，题库规模约 4 万时足够；代价是稠密化后单索引约 12 GB。

#### 可选句向量

`SentenceTransformerEncoder`，默认 `BAAI/bge-small-zh-v1.5`（约 33M 参数、384 维）。入库时 `--encoder sbert`。本仓库当前索引**未使用** SBERT。若改用 SBERT，向量会从 8 万维降到数百维，内存下降两个数量级，但需重新 ingest，且中英混合题库要评估英文 MATH 的召回。

#### 近邻检索

`VectorIndex`：向量已 L2 归一，内积 = 余弦。

1. 若安装 `faiss-cpu`：`IndexFlatIP` 精确内积（会再拷贝一份矩阵，内存接近翻倍）。
2. 否则：NumPy `argpartition` 取 top-k。本机**未装 Faiss**，走 NumPy。

4 万条、8 万维的暴力检索在 16 线程 Ryzen 上仍可接受（文本查询约 0.2–0.4 s，主要时间在向量化而非 top-k）。

### 4.6 原题、变式与精排（`pipeline/`）

**没有交叉编码器、没有学习 to-rank。** 全部是规则 + 上述相似度。

#### 原题（`filter_original.py`）

必须同时通过：

1. **题干门**：公式开时先遮公式再比叙述。数量一致且表面相似 ≥ `t_same`（图搜用 `t_ocr_same`）；或规范化后包含关系（OCR 把图注拼进题干时的容忍）。
2. **公式门**（仅公式开）：模板兼容，或拆成原子公式集合相等。
3. **附图门**：任一侧无图则通过；否则墨迹余弦或 pHash 过阈值。

#### 变式（`variant.py`）

非原题且数量不同、结构分 ≥ `t_var` → `variant`。结构分过低 → `unrelated`。短题干且附图明显不同 → 强制 `unrelated`（避免「求 x」配不同几何图被当成变式）。

#### 精排（`rerank.py`）

只保留原题或变式。原题最终分：

\[
1.2 + 0.1 \times \text{retrieval\_score}
\]

变式为结构、召回分、公式分、附图分、结构-表面差的线性组合，并减去表面分（抑制「字面很像但结构不够」）。排序关键字：`(不是原题, -final_score)`，因此原题永远在变式前面。

`cutoff`：低于 `min_final_score` 丢弃；与已保留条目同类型且表面相似 ≥ `t_same` 视为重复丢掉（**只比文本，不比图**）；满 3 条停止。

### 4.7 HTTP 与 CLI（`api/` / `cli.py`）

- FastAPI + Uvicorn。`POST /v1/search` 为 `multipart/form-data`（`text` / `image` / `math_ocr`）。
- 识图与检索放在线程池，避免阻塞事件循环；VLM 内部仍串行。
- `GET /health` 返回索引规模；`GET /v1/items/{id}/image` 返回入库时的本地配图。
- 静态页 `api/static/index.html` 提供浏览器检索与公式检测开关（记在 `localStorage`）。

### 4.8 评测（`pipeline/eval_metrics.py` + `data/eval/`）

- **文本金标**：把库中题干当查询，看金标 id 是否进入最多 3 条。偏乐观，测不到拍照 OCR。
- **渲染图**：`formula_10k` 按来源配额抽 10000 题，白底渲染（MATH / Geometry3K 用 Tectonic 编 LaTeX），再走完整识图管线。
- 指标：命中@3、首位、是否标成原题、误标其他原题、空结果、时延。

## 5. 评测结果摘要（formula_10k，2026-09-10）

索引 37645 条；查询 10000 条（APE 1328 / CM17K 4554 / Geometry3K 797 / MATH 3321）。Geometry3K 图搜关公式检测（题干 ∧ 附图）；其余开公式检测。

### 5.1 文本金标

| 分组 | 样本 | 命中@3 | 空结果 | 均耗时 |
|---|---:|---:|---:|---:|
| 总体 | 10000 | **92.7%** | 0.0% | 0.17 s |
| APE | 1328 | 100.0% | 0.0% | — |
| CM17K | 4554 | 92.1% | 0.0% | — |
| Geometry3K | 797 | 58.3% | 0.0% | 0.33 s |
| MATH | 3321 | 98.8% | 0.1% | 0.42 s |

Geometry3K 文本偏低，主要因为大量重复短题干（如 `Find x.`），金标按 **id** 计，而 `cutoff` 会把后续相同表面文本的原题折叠掉；文本通道看不见图。

### 5.2 渲染图（完整识图）

| 分组 | 样本 | 命中@3 | 空结果 | 均耗时 |
|---|---:|---:|---:|---:|
| 总体 | 10000 | **86.8%** | 8.2% | **3.90 s** |
| APE | 1328 | 99.5% | 0.4% | 3.48 s |
| CM17K | 4554 | 92.1% | 0.0% | 4.63 s |
| Geometry3K | 797 | 41.0% | 50.9% | 0.85 s |
| MATH | 3321 | 85.2% | 12.3% | 3.79 s |

图搜时延几乎全部在 VLM 读题（约 4 s/张）。Geometry3K 关公式后走 RapidOCR，时延降到 0.85 s，但 RapidOCR 会把图上数字读进题干，原题三门更严，空结果约一半。MATH 剩余约 15% 未命中，主要是公式模板对不齐、以及 `[asy]` 图未画进评测 PNG 导致召不回。

## 6. 模块—模型对照表

| 模块 | 是否深度学习 | 具体模型 / 算法 | 训练与否 |
|---|---|---|---|
| 数据加载 | 否 | 规则解析 | — |
| 文本规范化 / 公式模板 | 否 | 正则、数量替换 | — |
| 题干/结构相似 | 否 | difflib + 3-gram Jaccard | — |
| 召回编码 | 否（默认） | 字符 2–4 gram TF-IDF，80k 词 | 仅在题库上拟合 IDF |
| 召回编码（可选） | 是 | bge-small-zh-v1.5 | 用官方预训练，不微调 |
| 近邻 | 否 | NumPy 内积 或 Faiss IndexFlatIP | — |
| 文字框 | 是 | RapidOCR / PP-OCRv4 ONNX | 预训练 |
| 整图读题 | 是 | **PaddleOCR-VL** 或 Qwen2.5-VL-3B | 预训练，不微调 |
| 附图 | 否 | 16×16 墨迹网格 + pHash | — |
| 原题/变式/精排 | 否 | 阈值规则 + 线性加权 | — |
| 服务 | 否 | FastAPI / Uvicorn | — |

结论：系统是**检索管道**，不是端到端答题或生成模型。需要 GPU 的只有「公式检测开」时的视觉读题；题库匹配本身是 TF-IDF + 规则。

## 7. 部署形态

三种可落地的运行方式：

1. **仅文本检索**：CLI `eqsearch search --text ...` 或 HTTP 只传 `text`。不加载 VLM，不需要 GPU。
2. **图搜、公式检测关**：RapidOCR 识题干 + 裁图。CPU 即可，适合几何配图为主、公式结构不单独过门。
3. **完整产品（默认）**：RapidOCR 裁图 + PaddleOCR-VL 读题 + 三门原题。需要 NVIDIA GPU 与 `paddlepaddle-gpu`。

进程模型：单 Uvicorn worker 即可；VLM 有全局锁，多 worker 会在 GPU 上争用显存。题库在启动时整库载入内存，不接外部向量数据库。

## 8. 部署硬件评估

评估依据：本机实测配置、索引体积、formula_10k 时延、以及各模型的参数量/精度。

### 8.1 实测机器（可运行完整管线）

| 项目 | 配置 |
|---|---|
| 整机 | ASUS TUF Gaming A15 FA507RM |
| CPU | AMD Ryzen 7 6800H，8 核 16 线程，3.2 GHz |
| 内存 | **32 GB**（约 31.2 GB 可用） |
| GPU | **RTX 3060 Laptop 6 GB**，驱动 572.47 |
| 读图 | PaddlePaddle 3.2.2 GPU + PaddleOCR 3.7（PaddleOCR-VL），权重缓存约 1.9 GB（`~/.paddlex`） |
| 索引 | 11.5 GB `vectors.npy` + 43 MB 条目 |
| 图搜时延 | 约 **3.5–4.6 s/查询**（公式开）；文本约 **0.2–0.4 s** |
| 并发 | 单请求串行（VLM 锁） |

6 GB 显存能跑通的前提是 `EQSEARCH_VL_MAX_SIDE=1024`。更大原图会在视觉编码器里涨显存直至卡住。

### 8.2 资源拆解

| 组件 | CPU | 内存 | 显存 | 磁盘 | 说明 |
|---|---|---|---|---|---|
| 稠密 TF-IDF 索引 | 召回时矩阵乘 | **≈12 GB 常驻** | 0 | 12 GB | 当前最大内存项 |
| 条目 JSON + Pydantic | 低 | 0.5–1 GB | 0 | 43 MB | 37645 条题干 |
| RapidOCR ONNX | 检测识别 | 0.3–0.8 GB | 0（默认 CPU） | ONNX 数十 MB | 每张图都跑 |
| PaddleOCR-VL | 预处理 | 1–2 GB | **约 4–6 GB** | ~2 GB 权重 | 公式开、图搜 |
| Qwen2.5-VL-3B FP16 | 可 CPU 但极慢 | 数 GB | **约 6–8 GB+** | ~7 GB 权重 | 回退方案；6 GB 卡很紧 |
| FastAPI / Python | 低 | 0.3 GB | 0 | — | |
| 操作系统余量 | — | 3–4 GB | — | — | Windows 不可忽略 |

把索引、Python、OCR、VLM 加在一起：完整图搜在 Windows 上需要大约 **20–26 GB 内存 + 6 GB 显存**。本机 32 GB 内存是合适的；**16 GB 内存大概率无法同时载入 12 GB 稠密索引和读图模型**。

未安装 Faiss。若安装 `faiss-cpu` 且仍保留一份 NumPy 副本，内存会再加约 12 GB，32 GB 机器会开始换页。要用 Faiss，应改为只保留 Faiss 索引或改用稀疏/低维向量。

### 8.3 推荐配置分档

#### A. 最低：仅文本检索（演示 / 内网工具）

| 项 | 建议 |
|---|---|
| CPU | 4 核以上 x86_64 |
| 内存 | **24 GB 起步，32 GB 稳妥** |
| GPU | 不需要 |
| 磁盘 | SSD ≥ 20 GB（系统 + 索引） |
| 系统 | Windows / Linux，Python 3.11+ |
| 并发 | 数路文本查询（受 8 万维矩阵乘限制，建议 ≤4） |
| 预期时延 | 0.2–0.5 s |

16 GB 内存仅在缩小题库（例如 `--limit` 数千条）或改成稀疏/SBERT 索引后才现实。

#### B. 常用：图搜但关闭公式检测

在 A 的基础上增加 RapidOCR。仍建议 32 GB 内存。GPU 可选。时延约 0.8–1.5 s/图。适合 Geometry3K 这类「图重要、公式门会误杀」的场景，但中英文公式题的原题判定会变松。

#### C. 产品默认：公式检测 + 拍照搜题（与本机一致）

| 项 | 最低可跑 | 建议生产 |
|---|---|---|
| GPU | NVIDIA **6 GB**（已验证 3060 Laptop） | **8 GB** 起（4060 / 3070 / T4 / A10） |
| CUDA | 与 `paddlepaddle-gpu` 3.2 匹配的驱动 | 生产环境固定驱动与 paddle 版本 |
| 内存 | **32 GB** | 32–64 GB |
| CPU | 6 核+ | 8 核+ |
| 磁盘 SSD | 30 GB | 50 GB+（日志、评测图、模型缓存） |
| 读图模型 | PaddleOCR-VL | 同左；不要与 Qwen 同时常驻 |
| 长边限制 | 必须 `EQSEARCH_VL_MAX_SIDE=1024` | 8 GB 以上可试 1280–1536 |
| 并发 | **1 路图搜 / GPU** | 多卡或排队；不要多 worker 抢一块 6 GB 卡 |
| 预期时延 | 3.5–5 s | 8 GB 卡可略降；吞吐仍受 VLM 限制 |

不要在 6 GB 卡上同时加载 PaddleOCR-VL 和 Qwen2.5-VL-3B。本机当前只装了前者，这是正确选择。

#### D. 不推荐 / 需要改造后再上

- **内存 16 GB + 当前稠密索引**：几乎会 OOM。
- **无 NVIDIA 的核显 / 纯 CPU 跑 PaddleOCR-VL 或 Qwen-3B**：延迟可达数十秒到数分钟，不能当交互检索。
- **Apple Silicon / 只装 CPU paddle**：本项目读图路径按 CUDA GPU 验证，未作为部署目标。
- **多用户同时拍照**：单锁单卡，需要请求队列或按 GPU 分片。
- **题库扩到百万级**：当前暴力 8 万维内积和 12 GB 稠密阵都不可扩展，必须改稀疏 TF-IDF、Faiss IVF/HNSW，或换成 384 维句向量。

### 8.4 若要降低硬件门槛

按收益排序：

1. **不要把 TF-IDF 转成稠密 80k 维**。保持 CSR 稀疏，查询时只做稀疏-稠密乘；内存可从 12 GB 降到数百 MB 量级。这是对 16 GB 机器最关键的改动。
2. 题库改用 **bge-small / 多语言模型** 的 384 维向量：`37645 × 384 × 4 B ≈ 58 MB`，32 GB 变成奢侈而不再是刚需。
3. 图搜继续用 **PaddleOCR-VL**，不要上 3B Qwen，除非有 ≥8 GB 显存且需要更强的英文 LaTeX。
4. 服务端对上传图强制长边 1024，避免客户端原图撑爆显存。
5. 安装 Faiss 前先确认不会双份存矩阵。

## 9. 结论

eqsearch 是一套**规则检索系统**：字符 TF-IDF 召回，题干 / 公式模板 / 附图三门判定原题，结构相似且数量不同判定变式，线性精排后最多返回 3 条。深度学习只出现在输入端——RapidOCR 框字、PaddleOCR-VL（或 Qwen2.5-VL-3B）把卷面抄成带 LaTeX 的题干——后续匹配不依赖 CLIP 类图像向量，也不对题型做分类检索。

在现有 37645 条索引上，文本金标命中@3 为 92.7%，渲染图完整管线为 86.8%，图搜平均约 4 秒。部署完整拍照检索，硬件上应同时满足：

- **内存 32 GB**（当前稠密索引约占 12 GB）
- **NVIDIA GPU 6 GB 起、8 GB 更稳**（PaddleOCR-VL；6 GB 必须限制图像长边）
- **按请求串行使用 GPU**

若只提供粘贴题干，可以去掉 GPU，但仍建议 24–32 GB 内存，除非先把索引改成稀疏或低维向量。题库再扩大时，应优先改造向量存储，而不是堆显卡。
